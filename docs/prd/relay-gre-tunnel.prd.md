# PRD: GRE-туннель вход ↔ хаб

Адреса в документе — RFC 5737: хаб `203.0.113.10`, вход 6 `198.51.100.42`, вход 5 `198.51.100.43`, выходы `192.0.2.x`.

## Проблема

Инцидент 20.11.2026 (`docs/incidents/2026-11-20.md`): на транзите VDSina → Timeweb битый член ECMP/LAG теряет все пакеты части 5-tuple в сторону входа 6. Сейчас это 40–60 % потоков, и один и тот же source port либо всегда проходит, либо всегда пропадает. Ping и сырые GRE/IPIP проходят 10/10: портов у них нет, хэш считается по адресам.

- TCP 443/80 входа идут через его nginx stream. Их уже чинят ретраи на новом 5-tuple (`816295c`).
- TCP 2443 (Дуб) и UDP 30000–65000 (Бамбук) идут через nft DNAT. DNAT повторять не умеет: каждый «плохой» поток клиента мёртв целиком.
- Вход 6 выведен из ротации SQL-ом (аудит 190). Вход 5 у того же провайдера почти здоров: теряет 1 из 20 tuple.

## Цель

Все пути вход → хаб идут через GRE-туннель между входом и хабом. У внешнего пакета нет портов, поэтому хэш ECMP одинаков для всех потоков, и путь либо работает целиком, либо целиком не работает. Не работает — монитор уводит вход из подписки.

## User stories

- Как **пользователь на мобильной сети**, я хочу, чтобы Дуб и Бамбук через резервный вход подключались с первого раза, а не в половине попыток.
- Как **владелец**, я хочу перевести вход на туннель одной командой, без возврата в ротацию, с замером до/после и автооткатом, если стало хуже.
- Как **владелец**, я хочу, чтобы новый или переустановленный вход сразу ставился с туннелем, а смена адреса хаба (мастер) переводила туннели сама.
- Как **владелец**, я хочу, чтобы при падении туннеля вход сам пропадал из подписки, а мне пришёл алерт.

## Подходы (brainstorm)

| Подход | Что даёт | Почему так / не так |
|---|---|---|
| **GRE на каждый вход (выбран)** | Один постоянный хэш на пару адресов: чинит 2443, UDP и 443/80 | Замерено: GRE 10/10 в обе стороны. ufw умеет `proto gre` |
| IPIP | То же, на 4 байта меньше накладных | ufw не умеет IPIP: правило пришлось бы держать мимо ufw |
| WireGuard / UDP-туннель | Шифрование | У внешнего UDP есть порты, хэш снова по 5-tuple. Внешний поток один, но если он попадёт на битый член — мёртв весь вход. Плюс лишний демон и ключи |
| 2443 в nginx stream с ретраями | Чинит Дуб | UDP не чинит. Полдня правок ради половины задачи |

## Решения (мои, на проверку владельцу)

1. **Адресация.** Пул `10.77.0.0/16`, по `/30` на вход: хаб `10.77.0.0 + 4·id + 1`, вход `+2`, точка-точка (`peer`). Вход 6 → хаб `10.77.0.25`, вход `10.77.0.26`. Поддерживаются id 1…16383. Пул проверяется на пересечение с маршрутами и адресами обоих концов до любых изменений.
2. **Интерфейсы.** На хабе `he-r<id>` (юнит `heyearth-tunnel-r<id>.service`), на входе `he-hub` (юнит `heyearth-tunnel.service`). GRE без ключа, `ttl 64`, MTU 1476. `local` и `remote` — публичные адреса: на хабе это `main_server_host`, с которого он и отвечает. Юниты — свои oneshot (`ip tunnel add … / ip link del`), без netplan: сеть хаба и входа не перегенерируется.
3. **Вход, nft.** DNAT 2443 → `хаб_туннель:2443`, UDP 30000–65000 → `хаб_туннель:50443`. Masquerade в туннель, forward пропускает только ответы `хаб_туннель`. MSS clamp на SYN в `he-hub` (`rt mtu`).
4. **Вход, nginx.** Upstream: 2 копии `хаб_туннель` — основные, 6 копий публичного адреса хаба — `backup`. Всего 8 попыток за 10 с (ретраи `816295c` сохраняются). Туннель лёг — 443/80 уходят по публичному пути сами.
5. **Хаб.**
   - ufw: `allow proto gre from <вход> to <хаб>`.
   - Доверие PROXY: в файле входа (`/etc/nginx/heyearth-relays/<ip>.conf`) две строки — публичный адрес и адрес туннеля.
   - `heyearth-ddos-allow.sh` добавляет в `allow4` и в доверенный список nginx адреса туннелей (поле `peer` у `ip -o addr`). Так :8447 не режется, лимиты по адресу к туннелю не применяются.
   - Hysteria (`*:50443`, salamander) отвечает с адреса маршрута. Маршрут к `10.77.0.26` идёт через `he-r6` с `src 10.77.0.25` — это ровно тот адрес, на который вход делал DNAT. conntrack входа ответ примет.
   - Egress guard режет только новые TCP-соединения пользователей в `10/8`, ответы не трогает. Пользователи прокси до адресов туннеля по TCP не дотянутся.
6. **Туннель обязателен.** Если GRE до хаба не проходит (провайдер режет proto 47), вход не ставится, и шаг объясняет почему. Режима «без туннеля» в рецепте нет.
7. **Рецепт.** Новые шаги `relay_hub_tunnel` (хаб) и `relay_tunnel` (вход) — после sysctl, до правил. `relay_hub_trust` переезжает сразу за ними: хаб доверяет адресу туннеля до того, как nginx входа на него переключится.
   - Шаг хаба сравнивает «до» и «после» маршрут по умолчанию, маршрут-источник в интернет и все адреса хаба (кроме нового интерфейса). Разница → откат.
   - Пока шаг хаба ставит новый туннель, стоит таймер-предохранитель на 10 минут: если API упадёт посреди шага, туннель на хабе снимется сам.
   - Deprovision снимает оба конца.
   - Preflight: новая проверка «Туннель до Hub» (пул свободен, есть `ip_gre`). Проверка «Связь с Hub» повторяет каждый порт 3 раза: при потерях по tuple одна попытка врёт.
8. **Монитор.** Внешняя проверка входа (TLS через выход) идёт к :443 и к :2443. Для :2443 даётся одна повторная попытка на новом соединении. :443 при упавшем туннеле живёт через backup, а :2443 — только через туннель. Поэтому упавший туннель → 3 проверки подряд → вход `unhealthy` → строки входа уходят из подписки, алерт `relay-<id>-unreachable-external` подсказывает `systemctl status heyearth-tunnel`.
9. **Команда деплоя** `go run ./cmd/deploy --relay-tunnel ID [--relay-tunnel-check]`, по образцу `--relay-stream`:
   - отвязанный запуск на хабе, лог `/var/log/heyearth-relay-tunnel-<id>.log`;
   - `lifecycle` входа не трогается;
   - замер до и после с выхода: 100 TLS к `вход:2443` с разных source port и 100 UDP-проб Бамбука (salamander, Version Negotiation) на разные hop-порты;
   - плюс TLS-проверка :443 на самом входе и ping через туннель;
   - таймеры-предохранители на обоих концах (хаб 20 мин, вход 15 мин) снимаются только после «после ≥ 99 % и не хуже, чем до». Иначе откат обоих концов сразу;
   - ставит на хаб новый `heyearth-ddos-allow.sh` (тот же текст, что в `--setup-hardening`).

## Acceptance criteria

- [ ] `go test ./internal/config/ ./internal/provision/ ./cmd/deploy/ ./cmd/api/` зелёные; golden-эталоны nft/nginx/юнитов туннеля обновлены.
- [ ] Рецепт входа: свежая установка → туннель на обоих концах, повтор — ни одного изменения (Verify проходит, Apply не вызывается). Откат шага туннеля при провале проверки. Deprovision снимает оба конца.
- [ ] Шаг хаба отказывает (без изменений), если пул пересекается с маршрутом или адресом. Откатывается, если после изменения поменялись маршрут по умолчанию, источник или адреса хаба.
- [ ] На входе 6 туннель поднят, `lifecycle_state` остался `offline`.
- [ ] Матрица на входе 6, замер с выхода: TCP 2443 и UDP Бамбука «после» ≥ 99 %; «до» — как в инциденте (≈ 35–60 %).
- [ ] Внешняя проверка через выход: TLS к входу :443 и :2443 и проба Бамбука проходят.
- [ ] Падение туннеля (`systemctl stop heyearth-tunnel` на входе): :443 входа продолжает работать через backup, а проверка :2443 падает. Проверено в тесте монитора; на проде — по решению владельца.
- [ ] `docs/incidents/2026-11-20.md` дописан итог; runbook `docs/runbooks/relay-tunnel.md`.

## Out of scope

- Вернуть вход 6 в ротацию — решение владельца после замеров.
- Перевести вход 5 на туннель — его следующий провижн из админки сделает это сам. Когда — решает владелец.
- SSH хаб → вход через туннель (сейчас :22 теряется): отдельная задача.
- Шифрование туннеля. Внутри идут TLS/Reality и QUIC: GRE их не раскрывает.
- IPv6.

## Риски и open questions

- 🔴 **Хаб — единая точка отказа.** Изменения на хабе только добавляют: новый интерфейс с /32 из проверенного пула, одно правило ufw, одна строка доверия, nginx только после `nginx -t`. Плюс сравнение маршрутов до/после и таймер-предохранитель.
- 🔴 Старый API, переустановив вход, вернёт DNAT на публичный адрес. Туннель останется, но станет неиспользуемым. Поэтому новый API выкатывается вместе с `--relay-tunnel`, до любой переустановки входов.
- 🟡 Провайдер может резать GRE. Проверка рецепта это ловит, вход просто не ставится.
- 🟡 Смена адреса хаба: мастер переустанавливает входы, туннели переезжают вместе с `main_server_host`. Между шагом хаба и шагом входа туннель лежит секунды, 443/80 при этом идут через backup.
- 🟢 PMTU: внутри 1476. MSS clamp и собственный MSS хаба (1436) защищают TCP. QUIC сам находит размер (DPLPMTUD), потерянные пробы размера ему не вредят.

## Зависимости

- Блокируется на: «да» владельца на деплой (API + `--relay-tunnel 6`).
- Блокирует: возврат входа 6 в ротацию, `0kat` (монитор по потокам — с туннелем потерь по tuple быть не должно).

## Метрики успеха

- Таймауты `upstream timed out` в `error.log` входа 6: ≈ 0 вместо десятков за полчаса.
- Матрица с выхода через вход 6: ≥ 99 % по TCP 2443 и UDP.
