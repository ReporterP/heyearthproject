# PRD: Управление резервными входами на «Входах»

Адреса в документе — RFC 5737: хаб `203.0.113.10`, вход 5 `198.51.100.43`, вход 6 `198.51.100.42`.

## Проблема

20.11 (`docs/incidents/2026-11-20.md`) вход 6 терял 17–60 % подключений, а «Входы» весь день показывали «доступен». Монитор делает одну пробу в минуту и считает вход нездоровым только после трёх провалов подряд. Дальше всё делалось руками:

- **Вывод из ротации — SQL-ом** (`lifecycle_state online → offline`). После этого:
  - вход пропал со страницы, монитор перестал его проверять;
  - мастер смены адреса хаба его пропустил: он переустанавливает только `online`.
- **Вернуть вход можно только SQL-ом** или через «Настроить». «Настроить» в конце делает `activate` и сразу возвращает вход всем, без канарейки.
- **Удалить вход можно только на «Серверах»** (`NodeDrawer`).
- **GRE ставится всем.** С выкатки `a9098c8` каждая новая установка и «Переустановка» входа поднимает туннель, хотя владельцу он по умолчанию не нужен. Проверить заранее, пропустит ли провайдер GRE, нельзя.

## Цель

На «Входах» владелец:
- видит стабильность каждого входа за час и сутки;
- выводит вход из ротации и возвращает его с поточечной проверкой и через тестового пользователя;
- удаляет и добавляет вход;
- включает GRE только по своему выбору, после пробной проверки.

## Подходы (brainstorm, выбор владельца)

| Подход | Плюсы | Минусы |
|---|---|---|
| **A. Отдельное состояние ротации (выбран)**: `все` / `только тест` / `вне ротации`, lifecycle остаётся `online` | Монитор проверяет и выведенный вход: видно, починился ли он. Переустановка и мастер адреса хаба его не пропускают. «Только тест» и есть канарейка возврата | Новый столбец; фильтр там, где читают входы (`biz.ListRelayEntries`, `site_info`) |
| B. Как сейчас: `online ↔ offline` | Меньше кода | Выведенный вход не проверяется. GRE на нём не переключить без возврата в ротацию. Канарейку пришлось бы делать отдельно. «Отключён» и «выведен» не различить |

Добавление владельца к варианту A: **GRE включается только после пробной проверки туннеля из админки**.

## Решение

### 1. GRE — свойство входа, по умолчанию выключен (первый, отдельный коммит)

- **Флаг.** `servers.relay_tunnel BOOLEAN NOT NULL DEFAULT FALSE` (миграция). Входу 6 миграция ставит `TRUE` (`id = 6 AND role = 'relay'`): он уже на туннеле.
- **Без флага рецепт входа идёт путём до `352d8fc`:**
  - nft DNAT и nginx stream — на публичный адрес хаба, с ретраями `config.RelayNginxConf`;
  - правила ufw на хаб;
  - доверие хаба — только публичному адресу входа;
  - проверка «Туннель до Hub» в предпроверке — «не нужен».
- **Выключение — это тоже рецепт без флага.** Если на входе есть туннель, он снимается в конце рецепта: сначала nft и nginx переходят на публичный адрес, потом снимается конец туннеля на входе, потом на хабе. Подключения пользователей при этом не рвутся. На входе без туннеля эти шаги ничего не делают.
- **С флагом** — как сейчас.
- **`deploy --relay-tunnel ID`** ставит флаг, иначе следующая переустановка сняла бы туннель.
- **Мастер:** галочка «Туннель до Hub», по умолчанию снята.
- **«Входы», колонка «Туннель»:** «нет» / «GRE» и действие в панели входа.
  - **«Проверить туннель»** — новый вид задачи `tunnelcheck`, только для входа без туннеля:
    - предпроверка части туннеля: модуль `ip_gre`, свободный /30 на хабе и на входе;
    - поднимает оба конца с теми же защитами хаба, что у шага `relay_hub_tunnel`: отказ при пересечении пула, сравнение маршрутов и адресов до и после, таймер-предохранитель. Предохранитель в этой задаче не снимается, поэтому туннель исчезнет не позже чем через 10 мин, даже если API упадёт;
    - замер через туннель: ping, TCP к хабу на `:8447`, `:443`, `:2443` с 50 разных source port (≥ 95 %);
    - снимает оба конца. nft и nginx входа не трогаются, пользователи ничего не замечают.
  - **«Включить туннель»** доступно только после успешной «Проверить туннель» не старше 24 ч. Сохраняет флаг и запускает «Переустановку», с подтверждением и перечнем последствий.
  - **«Выключить туннель»** — флаг и «Переустановка», с подтверждением.

### 2. Все входы видны, состояние и причина

- `GET /api/admin/entries` отдаёт хаб и **все** входы при любом lifecycle. По каждому входу:
  - lifecycle;
  - ротация, причина, с какого времени и кто вывел;
  - флаг туннеля;
  - стабильность;
  - последние задачи «Проверить путь» и «Проверить туннель»: статус, время, итог.
- Колонка «Состояние»:
  - «в ротации»;
  - «только тест · с 20.11 18:00»;
  - «вне ротации · <причина>»;
  - для lifecycle: «настраивается», «ошибка настройки», «отключён».

### 3. Ротация

`entry_state.rotation` (`all` | `test` | `off`, по умолчанию `all`), `rotation_reason`, `rotation_at`, `rotation_by`.

| Состояние | Кто получает вход в подписке | Автоподмена и режим «Все через вход» | Монитор | Тревоги |
|---|---|---|---|---|
| `all` — в ротации | все | может быть целью | проверяет | да |
| `test` — только тест | только «Тестовый пользователь» «Входов» (`entry_failover_test_user`) | нет | проверяет | да |
| `off` — вне ротации | никто | нет | проверяет (здоровье и стабильность) | нет; открытые закрываются |

- **Новый вход из мастера** после установки сразу в `test`: новый вход — тоже изменение путей. Последний шаг мастера вместо «Включить для всех пользователей» говорит: вход уже у тестового пользователя, «Всем» — на «Входах» через сутки.
- **Вход 6 миграция переводит** из `offline` в `online` + `off` с причиной «20.11: провайдер терял 40–60 % потоков». Условие миграции: `lifecycle_state = 'offline'`, `role = 'relay'`. Вход сейчас настроен: туннель на новый адрес хаба, `--path-matrix 6` = PASS.
- **Действия.** Каждое требует `nodes.provision`, пишет аудит `entry_rotation` и увеличивает `subscription_version`:
  - **«Вывести из ротации»** (`all`/`test` → `off`). Причина обязательна, на сервере ничего не меняется. Отказ (409), если вход — цель режима «Все через вход» или активной автоподмены: сначала смените режим.
  - **«Вернуть: только тест»** (`off` → `test`). Нужны «Проверить путь» с PASS не старше 1 ч и заданный тестовый пользователь, плюс подтверждение.
  - **«Всем»** (`test` → `all`):
    - нужен PASS не старше 1 ч;
    - сам включает «Срочное обновление» на 24 ч, если оно не идёт дольше;
    - раньше 24 ч в `test` — только с вводом слова ДОСРОЧНО, в аудите `early: true`.
- **«Проверить путь»** — новый вид задачи `pathcheck`, только чтение. Это `--path-matrix` из API, прогресс показывает существующий `JobProgress`:
  - **хаб → вход:** TCP к `:443`, `:2443` с 50 source port;
  - **вход → хаб:** TCP к `:8447`, `:443`, `:2443` с 50 source port (по SSH на вход). У входа на туннеле — между адресами туннеля, а публичный путь печатается как BACKUP и в вердикт не идёт;
  - **через выход:** TLS к `:443`, `:2443` по 50 раз (≥ 99 %) и 50 проб Бамбука (≥ 95 %).

  Сырые группы — ≥ 95 %, вердикт — PASS или FAIL. Пробный скрипт и разбор вердикта общие с `cmd/deploy` (CLI работает как раньше).

### 4. Стабильность

- **Каждую минуту** через выход: 8 TLS-подключений к `:443`, 8 к `:2443` и 4 пробы Бамбука. У хаба — только `:443`. Каждое подключение новое, поэтому на каждом участке, включая вход ↔ хаб, у него свой 5-tuple.
- **Хранение:** `entry_probe_samples(entry_id, at, kind, ok, total)`, 3 дня, чистит retention.
- **Вердикт «доступен / недоступен» не меняется.** Он считается по первому подключению `:443`, первым двум `:2443` и обычной пробе Бамбука. Автоматический вывод из подписки работает как сейчас, новые подключения идут только в статистику.
- **Колонка «Стабильность»:** доля успешных за 1 ч и за 24 ч (худший из видов, подробности по видам — в подсказке и в панели входа). Цвет: ≥ 99 % — норма, 95–99 % — предупреждение, < 95 % — плохо. Меньше 20 проверок в окне — «мало данных».
- **Тревога `relay-<id>-unstable`** (warn): за 1 ч < 95 % хотя бы по одному виду при ≥ 30 проверках, для входов в `all` и `test`. Снимается при ≥ 98 %. Пропуск проверки (выход не работает) статистику не пишет.

### 5. Удаление и добавление

- **«Удалить вход»** вызывает существующие задачи с теми же подтверждениями (ввод имени, тексты `deprovisionConsequences` / `deleteConsequences`):
  - «Отключить» (deprovision, снимает пересылку на сервере);
  - затем «Удалить запись» (только `offline` / `pending`).
- **«Добавить вход»** — существующий мастер плюс галочка туннеля, новый вход стартует в `test`.

## User stories

- Как **владелец**, я хочу видеть на «Входах» долю успешных подключений к каждому входу за час и сутки, чтобы заметить частичные потери до жалоб.
- Как **владелец**, я хочу получить алерт, когда вход теряет больше 5 % подключений за час.
- Как **владелец**, я хочу вывести вход из ротации одной кнопкой с причиной и видеть его дальше на странице, с проверками.
- Как **владелец**, я хочу вернуть вход сначала только себе (тестовый пользователь) после поточечной проверки, а через сутки — всем со срочным обновлением.
- Как **владелец**, я хочу удалить вход и добавить новый, не уходя со страницы «Входы».
- Как **владелец**, я хочу ставить GRE только туда, где сам решил, и заранее проверить, что туннель у этого провайдера работает.

## Acceptance criteria

GRE:
- [ ] Рецепт входа без флага (Go-тест со стабами Remote) не содержит шагов поднятия туннеля. Правила nft — `RelayNftRuleset(хаб)`, nginx — `RelayNginxConf(хаб)`, доверие — без адреса туннеля.
- [ ] Рецепт с флагом совпадает с текущим (существующие тесты `relay_test.go`, `relay_tunnel_test.go` проходят).
- [ ] Выключение на входе с туннелем (тест): шаги rules и stream идут до снятия туннеля. После рецепта Verify шагов снятия проходит: `he-hub` / `he-r<id>` нет.
- [ ] «Проверить туннель» (тест) поднимает оба конца, меряет, снимает оба конца. Файлы nft и nginx входа не пишутся, предохранитель на хабе не снимается.
- [ ] `PUT /api/admin/entries/{id}/tunnel {"on":true}` без PASS «Проверить туннель» ≤ 24 ч → 409.
- [ ] После миграции у входа 6 `relay_tunnel = TRUE`, у входа 5 — `FALSE`.

Видимость и ротация:
- [ ] `GET /api/admin/entries` отдаёт вход 6 с `rotation: "off"`, причиной и временем.
- [ ] «Вывести» → `rotation = off`, `subscription_version + 1`, аудит. В подписке любого пользователя (URI и JSON) нет строк этого входа. На входе и на хабе ничего не изменилось.
- [ ] «Вернуть: только тест» без PASS ≤ 1 ч → 409. С PASS строки входа есть только у тестового пользователя.
- [ ] «Всем» без PASS ≤ 1 ч → 409. «Всем» включает «Срочное обновление» на 24 ч. Раньше 24 ч в `test` без слова ДОСРОЧНО → 400.
- [ ] Вывести цель режима «Все через вход» или активной автоподмены → 409.
- [ ] Монитор проверяет входы `off` и `test`, не делает их целью автоподмены, не поднимает тревог для `off`.
- [ ] `site_info.mobile_ready` и `ListRelayEntries` учитывают только `all`.

Стабильность:
- [ ] За минуту на вход пишется 3 строки `entry_probe_samples` (у хаба 1). 1 ч и 24 ч приходят в `GET /api/admin/entries`.
- [ ] Тревога при < 95 % за час (≥ 30 проверок), снятие при ≥ 98 % (тесты монитора).
- [ ] Существующие тесты вердикта монитора проходят без изменений ожиданий.

Общее:
- [ ] `go test ./cmd/... ./internal/...`, `npm test`, `npm run build` в `admin_web` зелёные.
- [ ] После деплоя — скриншот «Входов» на 1440 и 375 px.

## Out of scope

- Автоматический вывод входа по доле потерь (порог 25 % из `0kat`). Решение остаётся за владельцем, отдельная задача.
- Сырые проверки хаб ↔ вход в минутном мониторе: они только в «Проверить путь».
- SSH хаба до входов через туннель.
- Перевод входа 5 на туннель.
- Изменения в выводе `--path-matrix` CLI.

## Риски и open questions

- 🔴 **Откат API ниже этой версии после миграции.** Старый код считает «в ротации» любой `online`-вход: вход 6 (`off`) и входы `test` уйдут всем. Защита: gotcha в CLAUDE.md и runbook с SQL, который перед откатом переводит такие входы обратно в `offline`.
- 🔴 **Изменение путей.** «Всем» и новые входы проходят через `test`, PASS и срочное обновление (`docs/runbooks/subscription-changes.md`). Миграция входа 6 и фильтр по ротации выходят в одном релизе.
- 🟡 **«Проверить туннель» меняет хаб на время замера.** Защиты те же, что у `relay_hub_tunnel`, предохранитель остаётся взведённым.
- 🟡 **SSH хаба до входа 6** по публичному пути проходит через раз: «Проверить путь» повторяет подключение, как CLI (`relayStreamSSHTries`).
- 🟡 **Нагрузка монитора** вырастет примерно до 20 подключений в минуту на вход через один выход. Проверки параллельны, таймауты прежние.
- 🟢 Канареечный пользователь — тот же «Тестовый пользователь» «Входов». Он видит подписку как при аварии, вход `test` у него идёт строкой «· резерв N» и путём в «⚡ Авто».
