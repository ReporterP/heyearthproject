# Критический разбор архитектуры HiEarth: устойчивость VPN-пути

- Схема: https://claude.ai/artifact/5AY18JnhwkZH4CTfqfVaGY (исходник `docs/research/2026-11-20-hiearth-path.html`).
- Инцидент, с которого всё началось: `docs/incidents/2026-11-20.md`.
- В документе нет реальных адресов, имена узлов — как в админке.

## Выводы

1. **Самая дорогая слабость — хаб один на всё.** На одной VPS и VPN, и сайт, и оплаты, и БД, и монитор, и бот. Выключение 19.11 (33 минуты) прошло без единого алерта. Мобильная блокировка подсети хаба бьёт сразу по VPN и по сайту.
2. **Входы дали обход мобильной блокировки, но принесли свою точку отказа.**
   - Оба входа у одного провайдера, в одной площадке, на соседних адресах (/31). Похоже, это Сибирь: RTT 42 мс, маршрут через Ростелеком-Сибирь.
   - Путь вход → хаб — это транзит внутри РФ, и 20.11 он сломался для входа 6. Каждый круг через вход дороже на ≈85 мс.
3. **Автоматика смотрит не туда.**
   - Пробы `generate_204` (метод HEAD, сотни байт) и порог «3 провала подряд» не видят ни частичной потери потоков, ни «заморозки» после 16–20 КБ.
   - Монитор смотрит только из NL: мобильную РФ не видит никто.
4. **Главная рекомендация по «⚡ Авто».** Возвращать «только входы» не нужно. Хаб стоит оставить первым и заменить маленькую пробу большой (GET ≥ 64 КБ):
   - на мобильной сети проба хаба гарантированно упрётся в «заморозку» ТСПУ, и хаб выпадет сам;
   - на Wi‑Fi проба пройдёт, и пользователь получит путь короче на 85 мс.

   Это закрывает первую причину `1a92c81`. Вторую — VPN-трафик на адресе сайта — закрывает разделение ролей хаба (A1), а не удаление хаба из строки.

## 1. Наша система: что не так и почему

### 1.1 Хаб — единая точка отказа

| Что на хабе | Что будет, если хаб лёг или его адрес режут |
|---|---|
| xray (Берёза, Дуб), hysteria2 (Бамбук) | Весь VPN, в том числе через входы: они только пересылают трафик на хаб |
| Сайт, кабинет, оплата (вебхук ЮKassa на `hiearth.ru`), подписка | Новых оплат и подписок нет. `go.hiearth.ru` через вход помогает, только пока жив сам хаб |
| PostgreSQL | Резервная копия по таймеру, реплики нет |
| Монитор входов, туннелей, алерты, бот | Монитор и бот падают вместе с хабом: 19.11 11:07–11:40 ни одного алерта |

Мобильная блокировка подсети VDSina действует с 07–12.11, хаб — в Москве. Прямые пути на хаб с мобильной сети не работают: «· напрямую», Бамбук через хаб, сайт без туннеля. Смену адреса хаба делает отдельная сессия, но новый адрес в той же подсети или у того же провайдера даст тот же результат.

### 1.2 Входы

| Факт | Следствие |
|---|---|
| Оба входа у Timeweb, соседние адреса, общий маршрут через Ростелеком-Сибирь | Отказы коррелированы: площадка, провайдер, транзит. «Два входа» — это не два независимых пути |
| Режим `relay`, закреплён на вход 5 с 17.11 | Основные URI-строки всех клиентов идут через один вход. «· резерв» в этом режиме — как раз вход 6 |
| Вход → хаб: nginx stream, `proxy_connect_timeout 10s`, один upstream, без повтора | Потерянный поток — это 10 с ожидания, потом обрыв. Повтор с новым 5-tuple прошёл бы с вероятностью 40–60 % |
| :2443 и UDP — nft DNAT + masquerade | Потеря молчит: ни лога, ни повтора, ни метрики |
| Входы в Сибири | +≈85 мс на каждый круг (TLS, каждый запрос) по сравнению с хабом в Москве |
| unattended-upgrades обновил nginx на входе 6 в 05:00:57, на входе 5 в 05:07:18 | Оба входа могут рестартовать nginx в одно 7-минутное окно |

### 1.3 «⚡ Авто» (`cmd/api/subscription_json.go`)

- **Проба.** `burstObservatory.pingConfig` без `httpMethod`, поэтому по умолчанию `HEAD` на `generate_204`. В исходниках Xray (`app/observatory/burst/ping.go`) тело читается только при `GET`, код ответа не проверяется. Проба весит сотни байт, а ТСПУ замораживает соединение после ~16–20 КБ (см. §2), значит такая проба мобильную блокировку хаба не видит.
- **Допуск.** 2 провала из 5 проб — при потере 17 % потоков путь остаётся в пуле ~80 % времени.
- **Цены.** `costs` берёт первое совпадение (`app/router/weight.go`, `findValue`).
  - Без хаба правило `^p-r` ловит и `p-r5-xhttp`, поэтому у всех путей входов одна цена, и порядок «Берёза раньше Дуба» не действует.
  - После revert это не проявляется, но вернётся, как только хаб выпадет из пула.
- **xmux.** Дуб держит соединения десятки минут. Проба идёт по уже живому соединению, а новое может попасть в мёртвый поток.
- **Интервал подписки — 12 ч.** Серверная правка (убрать вход, поменять пробу) доходит до Happ только через 12 ч или после ручного обновления.

### 1.4 Мониторинг

| Проверка | Слепая зона |
|---|---|
| Монитор входов: TLS и UDP через выход NL, раз в минуту, 3 провала подряд | Частичная потеря: при 17 % потерь алерт приходит раз в несколько часов и закрывается через 2–4 минуты. Мобильная РФ |
| check-host | HTTP 403, результат игнорируется — взгляда из РФ нет вообще |
| Алерты через бота на хабе | Отказ самого хаба |
| Логи | Ни у xray, ни у stream на входах нет access log. Восстановить путь конкретного пользователя по логам нельзя, кроме Бамбука (hysteria пишет connect/disconnect) |

### 1.5 Выходы и туннели

- **Выход 3** стоит во всех платных тарифах с весом 1, хотя:
  - резервный туннель (ShadowTLS) не подключается: `dial tcp …:443 i/o timeout`, observatory пишет «exit-3.vr is dead»;
  - `latency_ms` утром доходил до 1745.
- **IPv6.** У выходов нет IPv6. В `hysteria2-client-2` за 105 минут 2 606 ошибок `dial tcp6`. Отказ мгновенный (`network unreachable`), так что это скорее шум журнала, чем задержка. Но клиенты, предпочитающие IPv6, тратят лишний круг.
- **Ping хаб → выход** — 40–44 мс сейчас, утром до 126. Через туннель ≈140 мс: заметная, но терпимая цена.

### 1.6 Мелочи, найденные по пути

- Исходящие с третьего адреса хаба не маршрутизируются: 0/24 к обоим входам. Передано сессии смены IP хаба.
- `servers.status` у входов — `offline`, хотя они работают. Поле для входов не ведётся, и это сбивает при чтении БД.

## 2. Что известно извне (2025–2026)

Обозначения уверенности: **высокая** — первоисточник; **средняя** — техотчёт сообщества; **низкая** — форум или одиночный пост. Хабр часть статей отдавал с HTTP 451, такие места помечены.

1. **«Заморозка» после ~16–20 КБ.** ТСПУ не рвёт соединение по RST, а замораживает его после ~15–20 КБ или ~25 пакетов от сервера к клиенту, если адрес сервера похож на хостинг. TLS-рукопожатие и маленькие ответы проходят. Уверенность **высокая**.
   - Cloudflare, июнь 2025: обрезка на 16 КБ для сайтов за Cloudflare у Ростелекома, МегаФона, Билайна, МТС, МГТС — https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet/
   - net4people/bbs #490, тред живой до 10.2026 — https://github.com/net4people/bbs/issues/490
   - **Для нас:** `generate_204` эту «заморозку» не видит в принципе. Проба должна быть больше 20 КБ.
2. **Белые списки на мобильных.** У ТСПУ есть исключения по SNI, а позже по CIDR. В режиме белого списка проходит только трафик к разрешённым подсетям.
   - Перечень 57 «социально значимых сервисов» Минцифры (09.2025, по «Коммерсанту»): https://theins.ru/news/284804 — уверенность **высокая** для самой политики.
   - Как устроено технически — net4people #490, уверенность **средняя**.
   - Какие хостинги в итоге проходят, известно только из форумов (уверенность **низкая**, https://github.com/kort0881/russia-whitelist/discussions/21):
     - Yandex Cloud проходит чаще других, белый адрес получить трудно;
     - VK Cloud — нестабильно;
     - Timeweb — «работает», один отзыв.
   - Наш опыт (VDSina режут, Timeweb пропускают) с этим согласуется. Гарантий нет: оператор может поменять список в любой момент.
3. **Волны по хостингам.** Habr 1047442 (06.2026) пишет о массовых сбоях 05.06.2026 «на Beget, TimeWeb, Selectel и др.». Уверенность **низкая**: это реконструкция автора. Он считает, что фильтр перешёл от сигнатур к поведению: подсеть/ASN + отпечаток TLS + число параллельных рукопожатий к одному SNI. https://habr.com/ru/articles/1047442/
4. **Блокировка зарубежных хостингов целыми сетями** (тесты 05–06.11.2026, опубликовано 11.11): Hetzner, DigitalOcean, Vultr, OVH и др. Дома — заморозка на ~25 пакетах, на мобильных у Билайна около 8 пакетов, режется только TCP. Уверенность **низкая/средняя**: одно анонимное исследование, перепечатанное СМИ. https://www.mentoday.ru/technics/news/11-11-2026/saity-zagrujayutsya-napolovinu-v-rossii-nachalas-blokirovka-zarubejnyh-hostingov-celymi-podsetyami/
   - **Для нас:** выходы в NL видны только хабу, а не пользователям. Наш туннель хаб → выход — тот же класс трафика «РФ-хостинг → зарубежный хостинг», и за ним надо следить отдельно.
5. **QUIC.** Масштабная SNI-зависимая цензура международного QUIC, FOCI 2026: https://www.petsymposium.org/foci/2026/foci-2026-0010.php — уверенность **высокая**. Про UDP/QUIC на мобильных к российским адресам данных нет; на форумах пишут, что Hysteria2 у T2 не работает (уверенность **низкая**). Метку «только Wi‑Fi» у Бамбука стоит оставить.
6. **RU → RU (дата-центр → дата-центр) и ТСПУ.** Нейтральных источников о фильтрации нет. Наш случай на входе 6 — не ТСПУ: потеря на уровне SYN/SYN-ACK строго по хэшу 5-tuple, это подпись ECMP/LAG.
7. **Что делают устойчивые сервисы** (в основном форумы и Хабр, уверенность **низкая/средняя**):
   - каскад «вход в крупном РФ-облаке → выход за рубежом»;
   - несколько провайдеров для входов;
   - XHTTP + Reality как основной транспорт;
   - мультиплексирование вместо множества параллельных TLS;
   - правдоподобный отпечаток браузера;
   - готовность в любой момент сменить адрес входа.

   Про CDN-фронтинг через Cloudflare в 2026 подтверждённых рабочих схем не нашлось: сам Cloudflare режется на 16 КБ.
8. **Health-check.** В документации Xray (https://xtls.github.io/config/observatory.html) у `burstObservatory` по умолчанию `generate_204` и `HEAD`; `httpMethod: "GET"` заставляет дочитать тело (проверено по исходнику `ping.go`). Готовых публичных конфигов с «большой пробой» не нашлось. Предложение ниже — наше.

Не нашлось первоисточников: официальной позиции РКН о конкретных протоколах; данных о ShadowTLS и SS-2022 в РФ за 2025–26; RIPE Atlas или мобильных «зондов» у других сервисов.

## 4. Когда возвращать «⚡ Авто» только через входы (Beads `heyearthproject-xa51`)

**Рекомендация: не возвращать в прежнем виде.** Причина `1a92c81` — «маленькая проба через хаб на мобильной сети проходит, а трафик умирает» — лечится пробой M1, а не удалением хаба.

С M1 «⚡ Авто» само выбирает правильно: на мобильной сети хаб выпадает, на Wi‑Fi остаётся и даёт −85 мс.

Если владелец всё же хочет «только входы» (например, чтобы VPN-трафика на адресе сайта не было до A1), то только при всех условиях:

1. Минимум два здоровых входа **у разных провайдеров или площадок** (A2). Сейчас оба — Timeweb, соседние адреса.
2. Работает монитор потоков вход ↔ хаб с автоисключением (M2).
3. На входах повтор с новым 5-tuple (Q2).
4. В «⚡ Авто» проба ≥ 32–64 КБ (M1) и исправлены цены (Q4).
5. Сторож хаба снаружи (Q3), потому что все входы всё равно ведут в хаб.

## 5. Не делать

- Не реагировать на алерт «вход недоступен снаружи» перезапуском nginx на входе: поломка в транзите, рестарт ничего не даст.
- Не включать для входов «авто»-режим (`auto`) в надежде на мобильные: монитор смотрит из NL, мобильную блокировку он не увидит.
- Не тестировать путь только `ping` и не судить по одному `curl`: потеря по 5-tuple видна только на десятке соединений с разными source port.
