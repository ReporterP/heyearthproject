## Фаза A — Деньги и доступ клиентов (P0)

### A1. Пробный тариф и автопродление
- **Код.** Новая подписка берёт `auto_renew` из `plans.auto_renew_default`; у free-trial там `false`. Сейчас это значение игнорируется: `biz/plans.go:534,549,582`.
- **Правило в `processAutoRenew`** (`subscription_cron.go:177`): бесплатный тариф (цена 0) продлевается только если подписка выдана по промокоду (`promocode_used` не пустой). Проверку `max_activations_per_user` добавить.
- **Данные на проде, с копией затронутых строк в таблицу-бэкап:**
  - **Пробные без промокода внутри своих 7 дней:** `auto_renew=false`, доступ сохраняется до конца срока.
  - **Пробные без промокода дольше 8 дней.** Это те, у кого были бесплатные автопродления (`payments amount=0` или журнал «Auto-renew … (Пробный)»): `is_blocked=true`, подписка заканчивается сейчас.
  - **Подписка без промокода, где длинный срок выставлен вручную** (есть запись в `admin_audit_log` или нет бесплатных продлений): не банить, показать владельцу списком.
- **Тест:**
  - новая пробная подписка → `auto_renew=false`;
  - бесплатная подписка без промокода не продлевается;
  - бесплатная подписка с промокодом продлевается.
- **Проверка на проде:** список забаненных (только префиксы ID) и счётчики до/после; в журнале нет «Auto-renew … (Пробный)» без промокода.

### A2. Промокоды — один путь применения
- **Два пути сейчас.** `payment/create` выбрасывает `freeTrialDays` и `trafficGiftBytes` (`payment_handlers.go:120`). `biz.ApplyPromocode` не проверяет `is_active` и тип кода.
- **Одна функция** `biz.RedeemPromocode(user, code, ctx)`:
  - регистр не важен;
  - проверяются `is_active`, срок, `max_uses`, `per_user_limit`, тариф (`applies_to_plans`);
  - тип кода определяет эффект: скидка — только при оплате; `free_trial` — `free_days` на `plan_id_granted`; `traffic_gift` — начисление трафика.
  - `current_uses` увеличивается только после успешной выдачи или оплаты.
- **Переходят на неё:** REST `apply-promocode`, `payment/create`, gRPC `ApplyPromocode`.
- **Тест:** таблица по типам кодов и всем отказам.

### A3. Убрать списания с карты — их заменяет кошелёк
- **Почему.** Владелец не настраивал и не будет настраивать рекуррентные платежи в ЮKassa (решение 13.11). Сейчас «автопродление с карты» работает только у тех, у кого ЮKassa всё-таки сохранила карту (2 карты на проде), а dunning-очередь пуста.
- **Удалить:**
  - сохранение карт (`save_card`, `saved_payment_methods`, `/user/cards*`, блок карт в кабинете);
  - рекуррентное списание в `processAutoRenew`;
  - dunning целиком: `payment_retry_queue`, `dunning_cron`, страница «Дунинг» в админке.
- **Автопродление** с этого момента списывает деньги с кошелька: задача W4.
- **Порядок.** A3 выкатывается вместе с W4, чтобы ни одна подписка не осталась без способа продления.
- **Данные.** Перед удалением таблиц сделать бэкап в `*_bak_20261113`.

### A4. Ссылки и статусы платежей
- **Объявление Happ «Продлите»** (`subscription_handler.go:653`) ведёт на существующую страницу оплаты `/payment`. Добавить и маршрут `/checkout` → `/payment`.
- **Возврат из кабинета.** Вместо `status=='completed'` использовать `biz.IsPaidPaymentStatus` (`cards_handlers.go:160`, `PaymentsHistoryPage.jsx:354`).
- **Платежи `pending` старше 24 ч:** сверить с ЮKassa и закрыть (`payment_sync`). На проде 18 таких с апреля.
- **Тесты** на каждый пункт.

### A5. Регистрация и сессия на сайте
- **Регистрация** (`RegisterPage.jsx:30,61`): после создания аккаунта показать экран «Сохраните ID» и не уводить в кабинет, пока клиент не нажмёт «Сохранил». `?redirect=` пробрасывается с регистрации на вход.
- **Общий `apiFetch` на сайте.** 401 определяется по статусу ответа, а не по тексту. На 503 — «временно недоступно», без «нет подписки». Сообщения по-русски.
- **Бэкенд:** ошибка БД при проверке сессии → 503 на всех `/user/*`, а не 401.
- **Проверка:** сборка сайта; в браузере регистрация → экран ID; протухший токен → страница входа.

### A6. Кабинет не ждёт сторонний сервис
- Убрать вызов `crypto.happ.su` из `/subscribe-token` (`subscription_handler.go:559`): сайт его не использует.
- На `/connect` оставить `happ://add/<url>` без зашифрованной ссылки.
- **Проверка:** время ответа `/subscribe-token` меньше 200 мс.

### A7. Лимит трафика одинаковый на всех протоколах
- **Сейчас:** Hysteria режет по квоте всегда, xray — никогда.
- **Правило:** квоту превысил → пользователь убран из xray, Hysteria и AWG до нового периода или оплаты. Флаг `quota_cutoff_enabled` по умолчанию `true`, переключатель в «Настройках».
- **Подписка по промокоду** получает лимит 0, то есть без лимита (решение владельца 3). Миграция выставляет `traffic_limit=0` у промокодных бесплатных подписок.
- **Тест:** превышение → нет в конфиге xray и отказ авторизации Hysteria; промокодная → есть.
- **Подписка меняется намеренно:** снимок до/после покажет разницу только у превысивших.

## Фаза W — Кошелёк (как в Steam)

**Идея владельца.**
- Пользователь пополняет кошелёк через ЮKassa разовыми платежами. Подписку и будущие услуги он оплачивает с кошелька.
- Автопродление списывает деньги с кошелька само.
- Тому, кто нажал «Оплатить подписку» с пустым кошельком, ничего про кошелёк понимать не нужно. Он платит в ЮKassa, кошелёк пополняется, и подписка сразу оплачивается с него.
- Кошелёк в кабинете виден явно и понятен.

**Юридически и с кассой — обязательно:**
- **Чеки по 54-ФЗ.**
  - При пополнении пробивается чек ЮKassa с `payment_mode = "advance"` и предметом «Пополнение лицевого счёта».
  - При оплате услуги с кошелька — второй чек «зачёт предоплаты» через API чеков ЮKassa (`POST /v3/receipts`, `settlements: [{type: "prepayment"}]`, предмет — услуга, `payment_mode = "full_payment"`).
  - Сверить по документации ЮKassa (Context7 / сайт) и проверить в тестовом магазине, если он есть.
- **Оферта.** Раздел «Баланс»: средства используются только для оплаты услуг сервиса, на счёт не возвращаются, проценты не начисляются. Это дословное требование владельца.
  - В финальном отчёте предупредить: ст. 32 ЗоЗПП даёт право отказаться от услуги и вернуть деньги за вычетом расходов, поэтому формулировку «безвозвратно» стоит показать юристу.
  - Возврат администратором (W6) остаётся как механизм для исключительных случаев.

### W1. Модель данных и проводки
- **Таблицы:**
  - `user_wallets(user_id PK → users.id, balance_kop BIGINT NOT NULL DEFAULT 0 CHECK (balance_kop >= 0), updated_at)`;
  - `wallet_transactions(id, user_id, amount_kop BIGINT /* +пополнение −списание */, kind TEXT, service TEXT, payment_id, subscription_id, referral_reward_id, admin_id, comment, balance_after_kop, idempotency_key TEXT UNIQUE, created_at)`.
  - Значения `kind`: `topup`, `purchase`, `auto_renew`, `referral_bonus`, `referral_welcome`, `admin_credit`, `admin_debit`, `refund`. Значения `service`: `vpn_subscription` (задел под будущие услуги).
- **Деньги в копейках.**
- **Все изменения** проходят через `biz.WalletApply(tx, userID, deltaKop, kind, idempotencyKey, refs)`: `SELECT … FOR UPDATE` на `user_wallets`, проверка «не уйти в минус», запись проводки, `balance_after`. Повтор с тем же ключом возвращает прежний результат, без двойного зачисления.
- **Тесты:** гонка двух списаний, идемпотентность, запрет минуса.

### W2. Пополнение
- `POST /api/v1/wallet/topup {amount_rub}` — минимум из настройки `wallet_min_topup_rub` (100).
- Создаёт платёж ЮKassa `kind=wallet_topup`, чек с авансом (см. выше), встроенный виджет или редирект, как сейчас.
- **Вебхук.** Платёж `succeeded` → `WalletApply(+сумма, topup, key=payment:<id>)` в одной транзакции со статусом платежа. Повторный вебхук ничего не меняет.
- `payment_sync` закрывает пополнения так же, как платежи сейчас.
- **Тесты:** вебхук дважды, отказ ЮKassa, отмена.

### W3. Оплата подписки: один поток для всех
- **Кнопка «Оплатить подписку»** у тарифа:
  - **Денег хватает.** Окно «Спишем 300 ₽ с кошелька. Останется 120 ₽. Подписка до 13.12» → `POST /api/v1/wallet/purchase {plan_id, promocode}`. Атомарно: списание, продление или активация, чек зачёта.
  - **Денег не хватает.** Окно «На кошельке 50 ₽. Пополним на 250 ₽ и сразу оплатим подписку». Сумма = недостающая, можно увеличить кнопками +100/+500 или полем. Создаётся платёж `wallet_topup` с `metadata.purchase = {plan_id, promocode}`.
- **Вебхук** такого платежа делает в одной транзакции: зачисление, затем покупку.
- **Страница возврата** опрашивает статус и показывает «Подписка активирована до DD.MM. На кошельке осталось N ₽».
- **Если покупка не удалась** (тариф выключили, промокод истёк): деньги остаются на кошельке, на экране ясно — «Кошелёк пополнен на 250 ₽, подписку оплатите кнопкой ниже». Алерт владельцу.
- **Промокоды:**
  - скидка уменьшает цену покупки;
  - `free_trial` и `traffic_gift` работают как в A2.
  - Одна функция `RedeemPromocode` для обоих путей.
- **Тесты:**
  - хватает / не хватает;
  - вебхук дважды;
  - покупка не удалась после пополнения;
  - промокод при покупке.

### W4. Автопродление с кошелька
- **Подписки с `auto_renew`,** которые заканчиваются в ближайшие 24 ч:
  - денег хватает → списание (`kind=auto_renew`, ключ `renew:<sub>:<period>`), продление, чек зачёта, письмо;
  - не хватает → объявление в подписке Happ «Пополните кошелёк: подписка закончится DD.MM» и письмо за 3 дня (E8).
- **Бесплатные подписки по промокоду** продлеваются бесплатно, как в A1, без кошелька.
- **Переключатель** «Автопродление с кошелька» в кабинете. По умолчанию включён для платных тарифов: денег без пополнения не спишет.
- **Тесты:** хватает / не хватает / дважды за период.

### W5. Кабинет: кошелёк явно и понятно
- **На главной кабинета** карточка «Кошелёк»: крупно баланс, «Пополнить», «История». Строка «Автопродление: спишем 300 ₽ 13.12 — денег хватает» или «не хватает 180 ₽».
- **Страница «Кошелёк»** (`/wallet`):
  - пополнение с готовыми суммами (300 / 900 / 3 000 и «своя»);
  - история с понятными подписями: «Пополнение», «Подписка „Всё включено“ до 13.12», «Бонус за друга», «Списано администратором: причина»;
  - текст «Что такое кошелёк» в 3 строки.
- **Страница тарифов и оплаты** работает по W3. Слово «кошелёк» человек видит, но разбираться в нём не обязан.
- **Правовые страницы:** раздел «Баланс» в оферте, FAQ.
- **Проверка:** сборка и скриншоты на мобильной ширине.

### W6. Админка: кошелёк пользователя
- **Карточка пользователя:**
  - баланс и проводки;
  - «Начислить» / «Списать» с обязательной причиной — право `wallet.adjust` (миграция прав), запись в аудит.
- **Платежи:** колонка «Тип» (пополнение / подписка / прочее).
- **Возврат пополнения** (`payments.refund`) — не больше текущего остатка кошелька: сначала `WalletApply(−)`, потом возврат ЮKassa.
- **Главная:** «На кошельках у пользователей N ₽» (обязательства), пополнения и списания за месяц.
- **Тест** прав и формы.

### W7. Переход
- Миграция создаёт кошельки с нулём всем пользователям.
- Активные подписки не меняются.
- Пользователям с `auto_renew` и платной подпиской за 3 дня до конца приходит объявление в Happ (и письмо, если есть адрес): «Продление теперь с кошелька — пополните заранее».

## Фаза R — Приведи друга

**Правило владельца.** Друг пришёл по ссылке и оплатил себе подписку → пригласившему +100 ₽ на кошелёк и другу +100 ₽. Суммы владелец настраивает в админке.

### R1. Данные
- В `users`: `referral_code` (короткий, уникальный, создаётся при первом показе), `referred_by_user_id` (ставится один раз), `referred_at`.
- Таблица `referral_rewards(id, referrer_id, friend_id UNIQUE, trigger_payment_id, referrer_kop, friend_kop, status, created_at)`.

### R2. Как друг привязывается
- **Ссылка `https://<site>/r/<code>`:** код запоминается в браузере на 30 дней, регистрация передаёт его в API, ставится `referred_by`.
- **Поле «Код друга»** в кабинете — в течение 7 дней после регистрации, если привязки ещё нет.
- **Запреты:** пригласить себя, привязку по кругу, смену пригласившего.
- **Тест** на все запреты.

### R3. Когда начисляется
- Срабатывает на первую покупку друга, оплаченную реальными деньгами: пополнение через ЮKassa, а не бонус и не промокод. Сумма покупки не меньше `referral_min_purchase_rub`.
- В одной транзакции:
  - `WalletApply(+referrer, referral_bonus)` пригласившему;
  - `WalletApply(+friend, referral_welcome)` другу;
  - запись в `referral_rewards`.
- Один раз на друга, идемпотентно.
- Лимит начислений одному пригласившему в месяц — `referral_monthly_cap` (0 = без лимита).
- Письмо или объявление: «Ваш друг оплатил подписку — +100 ₽ на кошелёк».
- **Тесты:**
  - покупка за бонусы — не считается;
  - вторая покупка — не считается;
  - вебхук дважды;
  - лимит.

### R4. Админка

## Фаза B — Серверы: добавить exit и вход за 5 минут, и «когда докупать»

Сценарий владельца после фазы:

1. Купил сервер.
2. Открыл «Серверы» → «Добавить».
3. Выбрал роль «Выход за границу» или «Вход в РФ».
4. Увидел на одном экране, что вставить у хостера: ключ Hub и какие порты открыть.
5. Ввёл IP и выбрал страну из списка.
6. «Проверить» → «Установить».
7. Через 5 минут сервер в списке с нагрузкой. Для входа — ещё «Проверить с телефона» и «Включить для всех».

### B1. Раздел «Серверы» — один для всех ролей
- **Вкладки:** «Выходы», «Входы в РФ», «Hub». Страница «Входы», вкладка «Ноды → Резервные входы» и `/servers/:id` сливаются сюда.
- **Строка сервера:**
  - статус (оба пути);
  - CPU %, RAM %, канал Мбит/с, подключения;
  - страна;
  - вес;
  - тарифы.
- **Карточка сервера** с вкладками «Обзор», «Нагрузка» (графики 24 ч / 7 д), «Настройки», «Опасная зона».
- **Hub** показан отдельной строкой с теми же метриками.
- **Тест:** модель строки (`node --test`).

### B2. Мастер: всё нужное на первом экране
- **Экран «Подготовьте сервер у хостера»:**
  - ключ Hub с кнопкой «Скопировать»;
  - для exit — порты: TCP 50052 только с адреса Hub, UDP 50443, TCP 10443;
  - для входа — TCP 443, 80, 2443 и UDP 30000–65000;
  - фраза «пароль root не нужен, если ключ вставлен».
- **Страна:** выпадающий список с флагом и названием, подсказка по GeoIP.
- **MTProxy** по умолчанию выключен.
- **Предпроверка с Hub:** TCP-коннект к SSH, после шага `node_agent` проверка 50052. Ошибка недоступности порта даётся до установки пакетов: «откройте порт N в панели хостера».
- **Тест:** модель шагов и тексты ошибок.

### B3. Метрики нод: честный статус
- **Сборщик** (`server_metrics_collector.go:98-140`):
  - ошибка `GetMetrics` пишет `status='offline'`;
  - не пишет `online` нодам вне `lifecycle_state='online'`;
  - одно gRPC-соединение на ноду с переиспользованием.
- **CPU** = `loadavg/nproc` в агенте, или проценты из `/proc/stat`.
- **Метрики входов (relay)** — по SSH ключом Hub раз в 5 минут: `/proc/stat`, `/proc/meminfo`, `/proc/net/dev`, `nf_conntrack_count`.
- **Hub** — локально.
- **Хранение:** таблица `server_metric_samples` (минутные сэмплы, 30 дней), почасовые p95 считаются запросом.
- **Тест:** парсеры `/proc`, решение offline.

### B4. Защита последнего выхода
- «Отключить» или «Удалить» единственный онлайн-выход требует ввода «ОТКЛЮЧИТЬ ВСЕХ» с текстом «у всех пользователей пропадёт интернет». Так же, как защита входа.
- **Тест** guard-функции.

### B5. «Мощность»: когда докупать
- **`CapacityHandler`** по всем ролям:
  - exit — сумма и запас N+1;
  - входы;
  - Hub.
- **Пороги** из исследования:
  - exit: CPU > 60 % или канал > 50 % порта;
  - вход: канал > 50 % или conntrack > 70 %;
  - Hub: CPU > 60 %;
  - трафик за месяц > 70 % лимита тарифа хостера.
- **Поля сервера, которые вводит владелец** (в «Настройках» карточки):
  - месячный лимит трафика у хостера, ТБ;
  - цена ₽/мес;
  - ядра (по умолчанию `nproc`).
- **Прогноз:** тренд дневных пиков за 14 дней → «упрётся через N недель». Плюс активные в сутки против расчётной ёмкости.
- **Виджет на главной и вкладка «Мощность»** в «Серверах»: вердикт словами («Всё в порядке» / «Скоро понадобится ещё exit — 1 ядро, 1 ГБ, ~700 ₽/мес»), стоимость на активного пользователя.
- **Алерт** «пора докупить» уровня warn, не чаще раза в сутки.
- **Тест:** вердикты, N+1, прогноз.

### B6. Чек-лист «Запуск» на главной
- **Пункты:** Hub работает → выходов ≥ 2 → вход в РФ добавлен → проверен с телефона → «Включить для всех» → A-записи DNS указывают на вход.
- Каждый пункт берётся из реального состояния. Рядом стоит кнопка в нужный мастер. Когда всё выполнено, чек-лист сворачивается.
- **Тест:** модель чек-листа.

### B7. Артефакты нод
- **Целостность артефакта:** `artifacts/node-agent` и `install-mtproxy.sh` загружаются через временный файл + `mv`, рядом пишется sha256. Мастер сверяет его перед установкой.
- **`quick_deploy.go`** обновляет артефакты, если они изменились.
- **Тест:** проверка sha256.

### B8. Рабочий запасной канал Hub → exit
- Reality по TCP с 12.11 режет ТСПУ (cudk.89).
- **Опыт на проде, как 12.11:** SSH-туннель (autossh `-D` как SOCKS для xray) и ShadowTLS v3 от Hub к exit. Каждый вариант гоняется не меньше суток под нагрузкой.
- **Победитель** становится запасным путём в рецепте exit и в мониторе туннелей вместо Reality.
- **Проверка:** при искусственно закрытом UDP трафик идёт по запасному каналу.

**Выкатка B:** API, затем админка. Проверка:
- текущий exit виден с CPU, RAM и каналом;
- Hub виден;
- «Мощность» даёт вердикт;
- мастер открывается с экраном «Подготовьте сервер».

**После фазы B владелец может заводить серверы.**

## Поправки при исполнении (13.11)

- **W, чеки.** Касса магазина — «Чеки от ЮKassa» (`fiscalization.provider = yoo_receipt`), а у неё нет признака «аванс» (`advance`): только `full_prepayment` и `full_payment`. Поэтому пополнение кошелька пробивается чеком «предоплата 100 %» (предмет — услуга), а оплата услуги с кошелька — закрывающим чеком `full_payment` с `settlements: [{type: "prepayment"}]` по `payment_id` пополнения. Если покупку оплатили несколько пополнений, чеков несколько (самое старое пополнение первым); бонусы и начисления админа чека не требуют.
- **A1, `max_activations_per_user` в автопродлении.** Проверка не нужна: бесплатный тариф без промокода больше не продлевается вовсе, а продление по промокоду — это продление промокода, а не новая активация тарифа. Бесплатно продлевается только подписка с активным промокодом типа `free_trial` (скидочный или выключенный код — нет).
- **A7, AWG.** Отсечку по квоте для AWG не делали: AWG («Пальма») удаляется в D7. До удаления лимит 0 у промокодных подписок не отрезает их от «Пальмы».
- **R3.** Бонус платится только за **первую** покупку друга, оплаченную реальными деньгами. По умолчанию её сумма должна быть не меньше 250 ₽ (`referral_min_purchase_rub`): иначе второй аккаунт самому себе окупался бы бонусами (100 + 100 ₽ за покупку в 100 ₽).
- **D3** (атомарный деплой сайта и загрузки, откат в `quick_deploy`) сделан до деплоя фазы A: без него сайт выкатывать нельзя.
- **A4.** Истёкшая подписка в Happ получает 403 без объявления, поэтому строка «Подписка истекла. Продлите →» не показывалась никогда; работают «истекает через N дн.» (ведут на `/payment`).
- **B, ревью.** Защита последнего выхода считает только **рабочие** выходы: онлайн, агент отвечает, туннель здоров, выход не отключается прямо сейчас. Проверка и запуск отключения идут по одному. Снятие тарифов с выхода (`/routing`) защитой не закрыто: выход без тарифов остаётся в общем пуле.
- **C4.** Фильтры «Истории подписок» не делали: страница удалена в C10 (история есть в карточке пользователя). Фильтры «Платежей» и «Журнала аудита» (даты, администратор) работают на сервере.
- **C10, «Дунинг».** После A3 карты и повторные списания удалены, дунинга больше нет. Его место — вкладка «Платежи → Не прошло продление»: подписки с автопродлением, которым не хватает денег в кошельке (закончились за неделю или закончатся за 3 дня). «Письма» тоже стали вкладкой «Платежей».
- **C13, хранение.** `dial_rate_log` хранит минуты **48 часов**, а 30 дней хранятся суточные сводки `dial_rate_daily`. Сырые минуты за 30 дней — это десятки миллионов строк при 1000 одновременных пользователей. Для карточки и главной хватает суток.
