# Подпроект 2 «Пул нод из админки» — спецификация

Второй из четырёх подпроектов (1 Стабилизация ✅ → **2 Пул нод** → 3 JSON-подписка «Лес» → 4 Безопасность).
Дизайн согласован с владельцем 2026-10-12 (вариант A «единое ядро провижининга по SSH с Hub», четыре фазы).

## Цель

Владелец сам покупает серверы и домены и **всё добавляет, проверяет и выводит из админки** — без CLI,
без SSH, без ручных правок. Падение или блокировка любой одной ноды не роняет сервис.

**Роли новых серверов** (решение владельца): зарубежные **exit** за Hub (как Амстердам) и **запасной
вход в РФ** — ретранслятор перед Hub (второй IP входа). Hub остаётся единственным «мозгом»
(БД, API, генерация конфигов). Второй полноценный Hub — вне объёма.

**Домены** (решение владельца): все назначения — подписка и API, адрес входа в профилях, сертификат
Бамбука, плюс общий реестр с проверкой DNS и выпуском сертификатов.

**Запасной вход для пользователя** (решение владельца): отдельные строки «… · резерв» **и** автоподмена
основного адреса в подписке при блокировке основного входа.

## Критерии успеха

| Что | Как проверяем | Цель |
|---|---|---|
| Новый exit из админки | от «Добавить» до `online` и трафика тарифов | ≤ 15 мин, без CLI/SSH, без перезапуска API |
| Второй exit безопасен | Бамбук и тарифы при 2+ exit (в т.ч. id ≥ 10) | работают; изоляция тарифов сохраняется |
| Устойчивость exit к блокировке UDP | Hysteria «Россия→заграница» задушена | трафик exit идёт по TCP-туннелю того же exit |
| Запасной вход | блокировка основного входа у пользователей | строки «· резерв» работают сразу; автоподмена в подписке ≤ 5 мин после детекта |
| Смена IP Hub | адрес входа на домене | правка одной DNS-записи, без переразводки подписок |
| Прогресс настройки | рестарт API во время провижининга | прогресс не теряется, задачу можно продолжить |
| Безопасность | секреты в ответах API админки | 0 (пароли, ключи, секреты туннелей не уходят в браузер) |
| Всё настраивается в админке | чек-лист раздела 7 | каждая функция подпроектов 1–2 видна и управляется из UI понятным языком |

**Не входит:** второй полноценный Hub, агент на нодах вместо SSH (вариант B — позже при росте), Happ
Provider ID (владелец отказался), JSON-подписка «Лес» (подпроект 3), gRPC-auth и ротация секретов
(подпроект 4), автоматизация DNS у регистратора.

## Раздел 1. Модель нод и данные

- `servers.role`: `exit` | `relay`. Hub в таблице не хранится. Принудительное `is_exit_node = true`
  убирается; генератор Xray выбирает exit по роли (колонка `is_exit_node` остаётся для совместимости,
  выводится из роли).
- Жизненный цикл для всех нод: `pending → provisioning → online ⇄ degraded → deprovisioning → (удалена |
  offline)`. Новая запись — `pending` (сейчас DEFAULT `online`). В маршрутизацию — только `online` +
  здоровый туннель (exit) / здоровый путь (relay).
- `provision_jobs` (id, server_id, kind: `provision|reprovision|deprovision|verify`, status:
  `queued|running|succeeded|failed|interrupted`, error, created/started/finished) и `provision_steps`
  (job_id, idx, name, status, started/finished, хвост вывода ≤ 8 КБ). Прогресс переживает рестарт API;
  при старте API незавершённые задачи → `interrupted`, перезапуск идёт с начала (шаги идемпотентны).
- Доверие к серверу: при первом подключении отпечаток ключа хоста показывается владельцу в мастере и
  подтверждается им (сверка с панелью хостера); хранится `ssh_host_key_fp` + `ssh_host_key_confirmed_at`;
  дальше подключения только с этим отпечатком (`InsecureIgnoreHostKey` убирается из teardown, MTProto,
  reconciler). Пароль — только зашифрованно (`SSH_ENCRYPTION_KEY` обязателен, при отсутствии —
  явная ошибка, а не тихий пропуск; ключ входит в whitelist `api.env`). После настройки Hub ставит на
  ноду свой SSH-ключ (ed25519, генерируется один раз на Hub) и ходит по нему; пароль остаётся запасным.
- Секреты (пароли, приватные ключи, `tunnel_*` секреты) **никогда** не возвращаются в ответах API админки.
- `domains` (фаза 4): name, purposes[] (`subscription`, `entry`, `bamboo_cert`), expected_target
  (`hub` | relay server_id), dns_status/dns_checked_at/dns_details, cert_status/cert_expires_at.
- `plan_servers` — без изменений схемы; запись привязки — в транзакции. `load_weight` — настоящий вес
  (раздел 3).

## Раздел 2. Ядро провижининга и рецепт exit

Пакет `internal/provision`, общий для админки и CLI:
- Задача = упорядоченные шаги; шаг = `Apply` + `Verify` (+ `Rollback`, где есть что откатывать).
- Удалённые файлы — атомарно (временный файл + `mv`), запись только при изменении (сверка sha256);
  сервис перезапускается только при изменении его конфига/бинарника; после перезапуска — проверка в двух
  точках (`is-active` + стабильный `NRestarts` за ~9 с); при неудаче — откат из `.bak`.
- Все шаблоны — из `internal/config` (одни на админку и CLI): Hysteria-сервер exit (тюнинг прода:
  окна 26843545/67108864, Brutal 100/100, ACL `ExitHysteriaACL` с MTProxy), hop-правило
  `ExitPortHopScript`, клиент туннеля `HubHysteriaClientYAML`, Xray exit с guard-правилами.
- API **никогда не перезапускает себя**; после изменения в БД — `RequestXraySync` / синк Hysteria-клиентов.
  Добавление exit — структурное изменение → ровно один перезапуск Xray.
- Выполнение — горутина API с записью в `provision_jobs/steps`; один job на ноду одновременно.

**Рецепт exit:**
1. Предпроверка (ОС Ubuntu/Debian x86_64, свободные порты, диск, время, доступ в интернет) — без
   изменений; понятная причина отказа.
2. База: sysctl (BBR, буферы), пакеты.
3. Фаервол: включается, только если уже включён; всегда открываются фактический SSH-порт, порт
   node-agent, MTProxy, туннели.
4. Hysteria-сервер (установщик со сверкой sha256, конфиг, ACL) + port-hopping.
5. **Запасной TCP-туннель:** Xray на exit с VLESS Reality (решение владельца) + guard-правила.
6. MTProxy (опция мастера).
7. node-agent с **индивидуальным** mTLS-сертификатом ноды (CA на Hub).
8. Hub: клиент туннеля из общего шаблона + юнит; проверка всего пути (`generate_204` через туннель,
   отдельно по Hysteria и по TCP) → `online`.
9. Привязка к тарифам из мастера (по умолчанию — все платные).

**Вывод ноды** (`deprovision`): перевод трафика на другие exit (нода исключается из балансеров → sync),
остановка правильных юнитов (`hysteria2`, `xray`, `node-agent`, `mtproxy`), снятие nft, смена пароля
туннеля, удаление клиента туннеля на Hub; запись удаляется или остаётся `offline` (выбор владельца).

**CLI** — аварийный путь, вызывает то же ядро (через SSH-туннель к БД, как сейчас).

## Раздел 3. Маршрутизация при нескольких exit и разминирование (фаза 1)

- **Селекторы (`07f7`):** теги `exit-<id>.hy` (Hysteria) и `exit-<id>.vr` (TCP Reality); селекторы
  `exit-<id>.` — без совпадений с `exit-<id>0…`. Дублирование тегов убирается; `load_weight` → вес
  через стратегию балансера (`leastLoad` + `costs`). Один перезапуск Xray при выкатке.
- **Два пути на exit:** observatory видит оба тега; в пределах exit приоритет — Hysteria, при отказе —
  TCP; exit считается мёртвым, только если мертвы оба. Health-монитор отслеживает оба пути отдельно.
- **Бамбук (`s6yc`, P0):** режим `dedicated` (порт :1091, `hub_tunnel_password`, юнит
  `hysteria2-client-express`) удаляется. Бамбук всегда идёт через туннель выбранного exit по его порту
  `1088+id`. Выбор exit — по сглаженному RTT (EWMA, α = 0.3) с гистерезисом: переключение не чаще раза в 10 мин и
  только если новый exit быстрее на ≥ 20 % (`7yrs`); `hysteria2-server` перезапускается только при реальной смене exit.
- **Тарифы:** запись `plan_servers` в транзакции; новый exit без привязки получает только catch-all —
  мастер предлагает привязку сразу.
- **Опасные действия (`smqe`):** `fetch_tunnel_creds`, `sync_tunnel`, `sync_metrics` убираются из UI и
  отклоняются бэкендом; вместо них «Проверить туннель» (только чтение: реальная проверка через туннель).
  `GET /servers/{id}` перестаёт отдавать секреты.
- Фаза 1 для пользователей ничего не меняет, кроме одного перезапуска Xray; на Амстердаме появляется
  запасной TCP-путь (Xray на exit уже стоит).

## Раздел 4. Запасной вход в РФ (фаза 3)

- **Ретранслятор (`role=relay`):** RU VPS у другого провайдера; nftables (одна транзакция) пересылает
  TCP 443, 2443 и UDP 50443 + hop-диапазон на те же порты Hub с SNAT (ответы через ретранслятор).
  Приложений и данных пользователей на нём нет. Hub видит IP ретранслятора как клиента (на квоты не
  влияет).
- **Рецепт:** предпроверка → `ip_forward` + conntrack → правила nft → юнит, поднимающий правила после
  перезагрузки → фаервол (SSH + проброшенные порты) + fail2ban на SSH.
- **Проверка входа:** через зарубежный exit — TLS к `<relay>:443` с SNI Reality и ответ Бамбука
  (VN-проба) через hop-порт ретранслятора; при успехе — `online`. Тем же раз в минуту проверяет монитор
  (по каждому входу отдельно) + check-host из РФ.
- **Подписка:** строки «Берёза · резерв», «Дуб · резерв», «🎋 Бамбук N only WiFi · резерв» на каждый
  здоровый резервный вход. **Автоподмена:** основной вход недоступен снаружи (3 проверки подряд) и есть
  здоровый резерв → основные строки получают адрес резерва; `Profile-Update-Interval` на время аварии
  4 → 1 ч; возврат — после 2 успехов и 30 мин стабильности; каждая подмена — алерт.
- **Ограничение:** если IP Hub заблокирован на стороне хостера (как 09.10), путь «ретранслятор → Hub»
  тоже не работает — спасает быстрая смена IP Hub (адрес входа-домен, фаза 4).

## Раздел 5. Реестр доменов (фаза 4)

- Страница «Домены»: добавить домен + назначение → инструкция по DNS-записям (A → IP Hub/входа) →
  «Проверить DNS» (несколько публичных резолверов, в т.ч. Яндекс — подмена на российской стороне) →
  «Выпустить сертификат» (Let's Encrypt HTTP-01 через :80 на Hub, автопродление, алерт за 14 дней).
- **Подписка и API:** на домене Hub отвечает только путями подписки и API (сайт и админка там не
  показываются); nginx-vhost и map :443 генерируются из реестра; новые ссылки подписки (сайт, письма,
  бот) выдаются на этом домене.
- **Адрес входа:** для каждого входа (Hub и каждый ретранслятор) — «IP» или «домен» в профилях;
  рекомендация: основной вход на домене, резервы на IP. XHTTP (Дуб) не привязан к совпадению адреса и
  `host`.
- **Сертификат Бамбука:** путь к сертификату Hysteria и SNI в строках Бамбука берутся из реестра
  (сейчас захардкожен `hiearth.ru`); после продления — перезапуск `hysteria2-server` хуком.
- **Ограничение:** без Happ Provider ID приложение не переключает уже сохранённую ссылку подписки на
  новый домен; новые ссылки выдаются на нейтральном домене, старые пользователи переходят постепенно.

## Раздел 6. Надёжность, тесты, выкатка

- Тесты: рецепты — на настоящем bash с заглушками (как в подпроекте 1); ядро — идемпотентность, откат,
  возобновление после `interrupted`; генератор Xray — golden для нескольких exit, двух туннелей,
  селекторов; подписка — golden для резервных строк и автоподмены; правила ретранслятора —
  лаборатория с network namespace (iptables-nft/nft как на проде).
- Ревью: на каждую задачу — спецификация + качество; на каждую фазу — интегрированное ревью.
- Выкатка по фазам с деплоем из чистого worktree и проверкой Бамбука/проб снаружи:
  1. разминирование и маршрутизация (один перезапуск Xray);
  2. мастер exit — владелец покупает сервер и добавляет при мне;
  3. резервный вход;
  4. домены;
  5. «Админка для владельца» — параллельно с фазами 2–4 (не трогает сеть).
- Админка — раздел 7: по фазам 1–4 + фаза 5 «Админка для владельца» (независима от сетевых фаз).

## Раздел 7. Админка для владельца

Исследование: `docs/research/2026-10-12-admin-panel-audit.md`. Принцип: владелец — не разработчик; каждая
функция подпроектов 1–2 видна и управляется из админки **понятным языком** («Берёза/Дуб/Бамбук», «вход»,
«выход за рубежом»), опасные действия — с объяснением последствий и вводом подтверждения, секреты — только
на запись, состояния — правдивые. Образец страницы настроек — `AlertsPage`.

### Структура навигации
- **ОБЗОР:** «Состояние» (новая первая страница), «Дашборд», «Трафик».
- **КЛИЕНТЫ:** «Пользователи», «Подписки», «Промокоды».
- **ДЕНЬГИ:** «Тарифы», «Платежи», «Письма и повторы».
- **СЕТЬ:** «Ноды» (выходы за рубежом / резервные входы в РФ), «Входы», «Домены», «Протоколы и маскировка»
  (вкл. карточки Бамбука и Пальмы), «Подмена доменов», «РФ-сервисы напрямую», «Telegram-прокси».
- **СИСТЕМА:** «Алерты», «Обслуживание», «Настройки» (блоки: Платежи, Почта, Юр. данные, Подписки),
  «Администраторы», «Журнал аудита», «SSH-ключи», «Релизы».
- **B2B:** «Компании», «Аналитика» (свёрнутая группа).

### Распределение по фазам
**Фаза 1 (безопасность и правда, до покупки серверов):**
- Опасные кнопки сервера убраны из UI и отклоняются бэкендом; «Проверить туннель» (только чтение).
- Секреты не уходят в браузер: `GET /servers/{id}`, `GET /settings` (ЮKassa, SMTP, obfs/stats Hysteria,
  ключ AWG) — без секретов; секретные поля — только на запись (как токен бота); редактор `reality-keys.json`
  и запись файлов на серверах — убраны (журналы — только чтение).
- **Возврат денег:** проверка права `payments.refund` на бэкенде; диалог с суммой и вводом подтверждения
  вместо `prompt()`; то же для cancel/check-status/resend.
- 403 больше не разлогинивает (показывается «нет прав»); навигация и палитра команд скрывают недоступное.
- Список нод отдаёт `lifecycle_state`, `mtproto_status`, `load_weight`; бейджи правдивые; фильтры работают.
- Старая «Добавить сервер» скрыта до фазы 2 (с пояснением); модалка прогресса всегда закрывается.
- Переключатель автотюнера — с предупреждением о ломке профилей; «Запустить сейчас» честно сообщает,
  если тюнер не активен; карточка **Бамбука** видна (статус, выбранный exit, возраст ротации obfs).
- Общий `POST /settings` — белый список ключей с валидацией и синком; `hub_main_server_host` подписан
  правдиво («домен сертификата Бамбука»), `main_server_host` и `site_url` — видны (только чтение до фаз 3–4).

**Фаза 2:** «Ноды» по ролям, мастер «Добавить ноду» (роль и страна → доступ и «Проверить подключение» →
**отпечаток ключа хоста, сверить с панелью хостера** → предпроверка → опции: MTProxy, тарифы, вес →
задача с шагами `JobProgress` на `provision_jobs` (переживает рестарт, «Повторить с шага») → проверка пути
по Hysteria и TCP → `online`); карточка ноды (Drawer): «Обзор» (оба пути, версии, отпечаток), «Тарифы и
вес», «Задачи», «Журналы», «Опасная зона» (переустановить/отключить/удалить с вводом подтверждения);
«SSH-ключи» показывают публичный ключ Hub. Примитивы `ui/`: Wizard/Stepper, Tabs, Switch, CopyButton,
ConfirmDanger.

**Фаза 3:** мастер ретранслятора (тот же мастер, рецепт `relay`); «Входы»: Hub и ретрансляторы,
доступность снаружи и из РФ, адрес «IP/домен», статус автоподмены и история, **предпросмотр строк
подписки** «… · резерв»; настройка интервала обновления подписки; алерты по каждому входу.

**Фаза 4:** «Домены»: реестр с назначениями, инструкция по A-записи, «Проверить DNS», «Выпустить
сертификат», сроки; сюда переезжают `main_server_host`, `hub_main_server_host`, `site_url`, `cdn_host`,
`mtproto_fronting_domain`; генерация vhost учитывает режим PROXY (слушатель 8446).

**Фаза 5 «Админка для владельца» (независимо от сетевых фаз):**
- **«Состояние»** — светофор по фактам: каждый вход (снаружи/из РФ), каждый exit по двум путям, Бамбук,
  Xray (шторм рестартов, ошибки синка), БД, сертификаты, бэкапы (локальный и копия), диск, fail-open квоты,
  доставка в Telegram; у каждого пункта — «что это значит» и «что делать» + ссылка; бэкенд
  `GET /admin/health` (активные инциденты `alertManager` + отметки последних проб).
- **«Обслуживание»** (только чтение + «Бэкап сейчас»): сервисы Hub и NRestarts, версии (стоит/закреплена),
  бэкапы, фаза egress guard, режим реальных IP + баннер «не деплоить сборки без зеркала», сертификаты,
  диск, журнал API.
- **«Настройки»** по блокам: Платежи (секреты только на запись + «Проверить подключение», тест-режим за
  подтверждением), Почта (+ тестовое письмо), Юр. данные, **Подписки** (досрочное продление; **отсечка
  по квоте** с показом «сейчас отключит N пользователей» и пояснением про цикл; интервал обновления);
  мёртвые карточки удалены.
- **«Протоколы и маскировка»:** SNI, отпечаток, DNS, mux, балансировщик, CDN, Пальма — только чтение,
  «Изменить» за предупреждением «пользователям придётся обновить подписку».
- **«Алерты»:** человеческие названия ключей, ссылка на «Состояние».
- **«Тарифы»:** названия протоколов понятным языком, привязка нод с пояснением, перед удалением — число
  подписчиков, аудит.
- Починка сломанного: создание админов/ролей, создание пользователей, колонка «План», правка SSH-ключа,
  затирание порта MTProto, фильтры подписок/платежей/аудита, хоткеи, «Сменить мой пароль».
- Единообразие: тема (очистка `style.css`, легаси-компоненты на токены, только тёмная Linear-тема,
  violet), `Dialog` вместо `confirm/prompt`, `apiFetch` вместо сырого `fetch`, мобильная вёрстка.
