# Подпроект 1 «Стабилизация» — спецификация

Первый из четырёх подпроектов эпика «VPN stability overhaul» (1 Стабилизация → 2 Пул нод из админки →
3 JSON-подписка → 4 Безопасность). Работает на текущем железе (Hub 203.0.113.225 + exit Амстердам
192.0.2.126), без новых серверов. Дизайн согласован с владельцем 2026-10-11.

## Цели и критерии успеха

| Цель | Метрика | Сейчас | Цель |
|---|---|---|---|
| Соединения не рвутся | перезапусков xray в сутки (`journalctl -u xray \| grep -c "Started"`) | 900–1 100 | ≤ 5 в обычный день |
| Нет утечки трафика через RU IP Hub | трафик пользователей через `direct` при мёртвых exit | возможен | 0, блок |
| Мёртвый exit видно | время до статуса `unhealthy` после падения exit | не детектится (Hysteria2) | ≤ 2 мин |
| Падение входа видно | время до алерта при блокировке IP входа | не было алерта | ≤ 5 мин |
| Канал Hub→exit | загрузка 25 МБ через туннель | 1,8 МБ/с (~15 Мбит/с) | ≥ 5,6 МБ/с (≥45 Мбит/с) или задокументированный предел железа |
| Бэкапы | возраст последнего бэкапа | 4,5 мес | ≤ 26 ч, копия вне Hub |

**Не входит** (другие подпроекты): новые ноды, роли нод, self-steal Reality, JSON-подписка, gRPC-auth,
SSH-ключи вместо пароля, Flutter.

## Часть 1. Конфиг без лишних перезапусков

### 1.1 Детерминированная сборка конфига (хотфикс шторма)
- `biz.ListActiveVlessClients` (`internal/biz/user.go:137`): добавить `ORDER BY u.user_id`; выборка
  `plan_servers` — `ORDER BY server_id`.
- Во всех местах `cmd/api/xray_sync.go`, где списки собираются из map или запросов без сортировки
  (пользователи в правилах, direct-домены/IP, селекторы балансеров, exit-ноды) — явная сортировка.
- Сравнение старого и нового конфига — канонический JSON (парсинг + повторная сериализация), а не побайтово
  сырых строк.
- Причина: `GROUP BY` без `ORDER BY` даёт произвольный порядок строк; ежеминутная запись статистики меняет
  физический порядок → diff → `systemctl restart xray` (`xray_sync.go:780`).

### 1.2 Горячие изменения через API xray (подход A)
- Включить в конфиге `api.services`: `HandlerService`, `RoutingService` (сейчас только `StatsService`, `xray_sync.go:699`).
- Правила тарифов: вместо одного правила на пользователя (`xray_sync.go:601`) — **одно правило на тариф**
  с `ruleTag` (`plan-<id>-users`, `plan-<id>-direct-domains`, `plan-<id>-direct-ip`) и списком `user`.
- Классификатор изменений в `SyncXrayConfig`:
  - **user-only diff** — изменились только `inbounds[*].settings.clients` и/или правила с тегами `plan-*`:
    1. добавленные/удалённые клиенты → `xray api adu` / `rmu` по каждому пользовательскому inbound;
    2. изменённые plan-правила → `xray api adrules` (замена по `ruleTag`);
    3. проверка: `inboundusercount` по каждому inbound == ожидаемому;
    4. файл конфига пишется атомарно (`.tmp.json` → `xray run -test` → rename) **без** рестарта;
  - **структурный diff** (inbound/outbound, ключи Reality, порты, exit-ноды, балансеры, DNS, policy) → как
    сейчас: тест + `systemctl restart xray`.
  - Любая ошибка API или несовпадение счётчиков → откат на рестарт (не хуже текущего поведения).
- Статистика: поскольку рестартов почти нет, перестаёт теряться интервал до 60 с на каждом рестарте.
- Счётчик рестартов в памяти; > 10 за скользящий час → алерт (часть 6).
- **Проверить на стенде до прода** (локальный xray той же версии 26.3.27): точная семантика `adrules`
  (замена по тегу сохраняет позицию правила? нужен ли флаг append), поведение `adu` для VLESS с `flow`,
  совместимость с Reality-inbound за nginx stream. Если `adrules` не сохраняет порядок — план-правила
  вынести в конец списка перед catch-all, где порядок между ними не важен.

## Часть 2. Маршрутизация без утечек

- Порядок outbounds: первым (default) — `block`; у всех балансировщиков `fallbackTag: "block"`.
  Явные правила для `direct-freedom` (RU direct, private) и `api` сохраняются.
- При отсутствии здоровых exit блокируются **все** пользовательские inbound: `vless-reality`,
  `vless-xhttp`, `socks-awg`, CDN-inbound (сейчас только первые два, `xray_sync.go:620`).
- Проверка exit-нод (`checkTunnelHealth`, `xray_sync.go:1203`): для `hysteria2` — реальный HTTP-запрос
  `https://www.gstatic.com/generate_204` через локальный SOCKS-порт туннеля, таймаут 5 с; гистерезис
  3 провала → unhealthy / 2 успеха → healthy сохраняется; RTT пишется в `servers.last_rtt_ms`.
- Мастер-UUID: убрать fallback на `app_settings.vless_uuid` в выдаче пользователю (`client_api.go:167`)
  и в подписке — при ошибке БД возвращать ошибку.

## Часть 3. Канал Hub → exit

- Обновить Hysteria `v2.6.1` → актуальная стабильная 2.x (на дату ресёрча `app/v2.13.0`) во всех местах
  установки: `cmd/deploy/hysteria2_hub.go:23`, `cmd/deploy/main.go:1953,2157`,
  `internal/admin/servers_handlers.go:1564,1762` — версия вынесена в одну константу. Перед обновлением
  сверить changelog на несовместимости конфигов/клиентов.
- Бенчмарк (скачивание 25 МБ через SOCKS туннеля, 3 прогона, медиана) для вариантов:
  1. текущий: Brutal, `bandwidth 100/100 mbps`;
  2. Brutal с полосой = измеренной реальной;
  3. BBR (без `bandwidth`/с профилем BBR новой версии);
  4. 2–3 параллельных туннеля (несколько hysteria-клиентов, балансировка в xray).
- Побеждает вариант с лучшей медианой при отсутствии деградации RTT; результаты — в документ ресёрча.
- Если упор в CPU exit (steal 48%) — фиксируем цифры; замена exit — в подпроекте 2.

## Часть 4. Чистка

- Автотюнер: `auto_tuner_enabled=false` (флаг уже есть, `auto_tuner.go:176`); код не удаляется.
- Удалить inbound `shadowsocks` :8388 и соответствующие ufw-правила.
- ufw: удалить правила для портов без слушателя (1080 tcp/udp, 8080, 4443, 5443, 9443, 44443, 30443) —
  каждый предварительно проверить `ss -lntup`. Скрипты деплоя/провижининга перестают их добавлять.
- Тарифы: убрать `socks`, `http` из `plans.allowed_protocols` (миграция); `main.go:643–661` перестаёт
  отдавать `socks5_*`/`http_proxy_*`; Clash-выдача — убрать socks/http-прокси.
- Удалить мёртвый пакет `internal/xray` (config_generator.go, tunnel_manager.go) после проверки, что он не
  импортируется.
- Убрать `xPaddingBytes` из `realitySettings` (игнорируется xray).
- Бамбук (Hysteria2) в подписке/опциях — только если тариф разрешает hysteria2.

## Часть 5. Эксплуатация

- Бэкап: systemd-timer на Hub, ежедневно 04:00 MSK: `pg_dump -Fc heyearth` + `/opt/heyearth/state`
  (ключи Reality) + сертификаты → `/opt/heyearth/backups/` (ротация 14 шт.) + копия на exit-ноду
  (scp/rsync по SSH). Записанная процедура восстановления в `docs/` + один прогон восстановления в
  отдельную БД с проверкой количества пользователей.
- fail2ban: jail `sshd` (5 попыток / 10 мин → бан 1 ч).
- journald: `SystemMaxUse=1G`.
- nginx stream: `proxy_timeout 3600s` (= `connIdle`), сейчас 10 мин по умолчанию.
- Все изменения на сервере — через код деплоя/провижининга (не ручные правки), чтобы пережили
  переустановку.

## Часть 6. Мониторинг и алерты в Telegram

- Настройки в админке (app_settings): `alert_telegram_bot_token`, `alert_telegram_chat_id`,
  кнопка «Отправить тест». Токен хранится как секрет (не отдаётся в API в открытом виде).
- Модуль алертов в API: дедупликация по ключу события, cooldown 30 мин на повтор, сообщение о
  восстановлении, журнал событий в БД (видно в админке).
- События:

| Событие | Условие | Уровень |
|---|---|---|
| exit down / up | гистерезис health-check | warn |
| все exit мертвы | 0 healthy | critical |
| шторм рестартов | > 10 рестартов xray за час | critical |
| вход недоступен снаружи | 3 подряд провала loop-пробы | critical |
| вход недоступен из РФ | 2 подряд провала check-host (RU-узлы) | warn |
| сертификат | < 14 дней до истечения | warn |
| бэкап | последний старше 26 ч или ошибка | warn |
| диск | > 85% | warn |

- **Loop-проба (раз в минуту):** Hub делает TLS-запрос к своему публичному входу (`https://<entry>/`
  с SNI сайта и отдельно TLS-рукопожатие с Reality-SNI) **через SOCKS туннеля exit** — трафик выходит из
  Амстердама и возвращается на публичный IP Hub, то есть проверяется входящий путь извне.
- **check-host (раз в 15 мин):** `check-tcp` + `check-http` на вход с RU-узлов check-host.net,
  результат забирается через их API; недоступность check-host не считается падением входа.

## Порядок раскатки

1. 1.1 хотфикс сортировки → деплой → сутки наблюдения за счётчиком рестартов.
2. Часть 6 (алерты) рано — чтобы следующие шаги шли под мониторингом.
3. Часть 2 (без утечек + health-check) → деплой.
4. 1.2 горячие изменения (после стенда) → деплой.
5. Часть 4 (чистка) → часть 5 (эксплуатация) → часть 3 (Hysteria + бенчмарк).

Каждый шаг: `go build ./...` → деплой → `systemctl status` → проверка через каждый вход
(Берёза/Дуб/Бамбук реальным клиентом через новый IP) → метрика из таблицы целей.

## Риски

- `adu/rmu/adrules` ведут себя иначе, чем ожидается → стенд + автоматический откат на рестарт.
- `block` по умолчанию отрежет какой-то легитимный трафик без явного правила (например, внутренний DNS
  xray) → перед деплоем прогон `xray run -test` и запросы через каждый inbound на стенде с конфигом прода.
- Обновление Hysteria ломает клиентов Happ → проверить Бамбук реальным Happ до раскатки на exit;
  откат = предыдущий бинарь.
- Удаление ufw-правил закроет что-то нужное → проверка `ss` перед каждым правилом.
- Бенчмарк туннеля нагружает общий канал → прогонять ночью, коротко.
